## 2026-10-25 - F4: Vendors and Helpers Sign Up From Their Invite

Scope: close F4 so a real vendor or helper with no account can go from an
invite link to their scoped workspace without a seed script.

### Changed

- `lib/invites/claim.ts` (new, pure): invite validity, account mismatch, and
  the signed-out entry decision (signup / login / invalid), shared by the page
  and both actions.
- `lib/actions/invites.ts`: new `signupFromInviteAction` (email and role read
  from the invite, never the form; signup rate limit; re-checks the invite;
  then claims and signs in). `acceptInviteAction` and the new action share an
  internal `claimInviteForUser`, which claims with
  `UPDATE ... WHERE status = 'pending'` so two simultaneous accepts cannot both
  win. `invite_accepted` logs `viaSignup: true` on the signup path.
- `app/accept-invite/page.tsx`: signed-out visitors now see the signup form
  (no account), go to login (account exists), or get the reason (invalid
  invite), instead of always bouncing to login.
- `components/InviteSignupForm.tsx` (new): read-only invited email, name,
  password.
- `lib/auth/forms.ts`: `parseInviteSignupFields` (name + password only).
- `scripts/ux-invite-signup-smoke.ts` + `npm run ux:invite-signup` (new).
- Docs: flow 05 rewritten to the shipped behavior, change record
  `docs/09-changes/2026-10-25-f4-invite-signup.md`, F4 marked fixed in the
  findings register, system map, flow 01, constraints, code map, test
  strategy and README. New screenshot `screenshots/10-invite-signup.png`.

### Validation

  0 production vulnerabilities, no schema drift, build.
- Ran the app against a local Postgres 16 behind a minimal Neon-HTTP
  stand-in, so the real `@neondatabase/serverless` driver ran unchanged.
  All 13 migrations, including `0012` (`auth_attempts`), applied cleanly.
  - `ux:invite-signup` passed: new vendor and helper sign up and land in
    their workspaces; DB shows the right role, accepted invite, `viaSignup`.
  - `ux:invite` and `ux:public` still pass.
  - Live checks passed: used, expired and unknown invites show a message and no

## 2026-10-08 - Phase 0 Hygiene (fail-closed defaults and repo hygiene)

Scope: close the cheap, high-risk defaults found in the 2026-10-08 code review
before any structural work. No workflow or schema change.

### Changed

- **File privacy fails closed.** `blobAccessMode()` now returns `private`
  unless `BLOB_ACCESS=public` is set explicitly; unset, empty and mistyped
  values all mean `private`. `npm run poc:ready` treats an unset value as ready,
  **blocks** `public` when `APP_URL` is not localhost, only warns on localhost,
  and warns on an unrecognized value.
- **Seed guard.** `db:seed` now refuses a hosted `DATABASE_URL` (Neon always
  counts as hosted) unless `SEED_PASSWORD` is set to 12+ characters and is not
  `password123`. The check runs before any connection is made. New modules:
  `lib/local-host.ts`, `lib/seed-guard.ts`.
- **Dependency and runtime hygiene.** Pinned `next-auth` to
  `5.0.0-beta.32` (the installed version; no behavior change). Removed
  `@types/bcryptjs` (bcryptjs 3 ships its own types). Added
  `engines.node >= 22` and `.nvmrc` (`22`); CI now reads the Node version from
  `.nvmrc`.
- **README.** The decision-log claim is narrowed to "key steps" (the code does
  not log every step, and the log is deleted with its request; see review F8).
  Quickstart notes that `SEED_PASSWORD` is needed.
- **Docs.** Updated `.env.local.example`, `docs/DEPLOYMENT.md`, the P0 rollout
  runbook (the rollback step is now "set `BLOB_ACCESS=public`", because unsetting
  it means `private`), the file-upload flow doc and the findings register.
- Moved two untracked files out of the repo (an older README copy and a chat
  transcript) to a sibling folder outside version control.

### Why

A forgotten environment variable should never publish uploads, and a database
reachable from the internet should never receive a well-known password. Both
were one `.env` mistake away. The readiness gate also had no way to fail on a
public store.

### Validation

- `npx tsc --noEmit` and `npx eslint .` clean.
- `npm test`: 35 files, 331 tests pass (was 34 files, 318). New:
  `seed-guard.test.ts`; extended `blob-paths.test.ts` and
  `poc-readiness.test.ts`.
- `scripts/seed.ts` run against a fake hosted URL with no password and with
  `password123` refuses with exit 1 before connecting.
- `npm run db:generate` reports no schema changes; `git diff -- drizzle` clean.
- `npm run build` succeeds.
- `npm run audit:prod` first failed with two high advisories in production
  dependencies (`sharp` < 0.35.5, `source-map-js` 1.0.0 - 1.2.1). They were
  already in the committed `HEAD` lockfile (checked by auditing the unmodified
  lockfile), so they were not caused by this change; they were published after
  the previous "Fix production dependency audit" commit.
- **Resolved in a separate commit** with `npm audit fix` (no `--force`): six
  patch-level bumps (`sharp` 0.35.5 and `source-map-js` 1.2.2 in production;
  `drizzle-kit` 0.31.11 and two `brace-expansion` copies in dev tooling). Only
  `package-lock.json` changed. `npm run verify` now passes end to end: 35 test
  files / 331 tests, 0 production vulnerabilities, no schema drift, build ok.
- Lesson: the first `npm audit fix` updated the lockfile but not the files in
  `node_modules` (they were still dated before the fix), so a first green
  `verify` was not proof. Deleting `node_modules/.package-lock.json` and
  running `npm install` synced the files, and `verify` was re-run against them.

### Follow-Up

- **Before deploying this change** to any environment that still uses the old
  public Blob store, set `BLOB_ACCESS=public` there first (or finish the
  private-store switch in the runbook). Otherwise uploads fail with an
  access-mode error. Local `.env.local` files without `BLOB_ACCESS` are
  affected the same way.
- Still open, dev tooling only: `npm audit` (without `--omit=dev`) reports
  advisories such as `braces` (via `eslint-config-next`). Their only fix is
  `npm audit fix --force`, a breaking downgrade of `eslint-config-next`, so they
  are left alone. The PR gate audits production dependencies only. Moving the
  audit to a scheduled job is still planned for Phase 7.
- The database behind a developer `.env.local` was found without migration 0012
  (`auth_attempts`): 12 of 13 migrations applied, so login and signup rate
  limiting was silently failing open there. Apply with `npm run db:migrate`
  (additive: one table and one index) and confirm the target database.
- `ux:full-loop` and `ux:invite` insert users with a hardcoded password straight
  into whatever `DATABASE_URL` points at. Give them the same hosted-database
  guard.
